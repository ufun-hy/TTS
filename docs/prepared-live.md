# 首轮准备与持续随机智播

## 泛化与首轮音频准备同时进行

文本准备页默认勾选“泛化时同步准备首轮音频”。开始普通泛化或整组泛化时会保存项目并启动后台准备；每批/每组泛化保存后更新计划，文字模型继续处理下一批，同时一个后台 TTS 线程逐块合成。也可对已有候选点击“准备首轮音频”，或随时“暂停准备”。提前准备不会向 Windows 队列发送音频，也不会自动开播。

候选只在首次进入准备计划时独立随机选择；后续批次追加不重选之前的单元。整组模式按完整组选择一个版本。遇到未完成单元/组只准备其前面的连续部分；不完整句子和仍可能吸收下一批文字的最后一块暂不合成，全文完成后才释放尾块。现有合块算法保持不变。

保存编辑、人工确认/恢复屏蔽或音色变化时，计划重新校验，仅匹配当前文本及音色指纹的音频计为已准备。未改变的块可以复用；修改长度影响后续合块边界时，这些受影响块也需重新准备。旧的在途合成结果不计入新计划进度。实时日期/时间占位符沿用提前准备报错规则。

首个稳定完整音频块准备好后，即可进入直播页并点击“开启语音传输”，无需全文泛化完成。点击前先保存，服务端从已保存项目重新校验连续完成的前缀及音色，沿用首轮选择与 WAV；现有后台 TTS 线程继续准备，直播线程只按顺序领取 ready 块。`/api/live/start` 以 `project_id` 和 `stream_preparation: true` 启用此路径。旧的完整稿 API 路径保留兼容。

已有音频按顺序发送，后续完整块追加到同一个 session，sequence 连续递增；临时追上准备进度时只等待新内容，不结束首轮或提前循环。全文首轮全部发送后，加载最新完整候选池进入下一轮随机合成。没有 ACK 数量、Windows 水位或在线状态发送限制，也不添加兜底。

发送时固定该块涉及的话术单元及其之前的前缀；整组模式固定涉及的完整组。未发送且未与已发送块共享单元/组的内容仍可编辑并重新准备。已固定单元/组的编辑保存在项目中，首轮使用原内容，第二轮采用最新完整候选池。已接收音频不能撤回。删除/重排已发送前缀、切换声音或修改声音资产需要停止后重新开启。直播暂停/继续同时控制后续准备和发送；停止或错误会停止后续准备，已发出的同步请求允许返回。接入期间准备页按钮禁用，统一使用直播控制。

运行数据放在 `runtime/text-studio/audio-preparation/<project_id>/plan.json` 和共用的 `audio/`，与项目正文及源码分开。刷新页面会恢复进度；服务重启保留计划和音频，但不会自动启动 GPU 工作，点击继续即可恢复。一次只主动准备一个项目，切换到新项目开始准备会暂停原项目；已有文件不自动删除。

职责：`server/first_round_plan.py` 负责选择与稳定分块，`server/first_round_preparation.py` 负责后台串行合成和持久化，`web/text-studio-preparation.js` 展示状态并控制开始/暂停。相关接口为 `/api/preparation/start`、`/api/preparation/pause`、`/api/preparation/status?project_id=...`。TTS 不可用或某个组需处理时，项目保存和文字泛化仍可继续。

普通直播提交每个话术单元的所有候选和各自的人工确认记录，服务端先过滤不可播内容，再为每个单元独立随机选一个候选，按原稿顺序合块。启用提前传输后首轮边准备边发送，随后继续重新选候选、合块、合成、发送。整组模式仍按组选择完整版本，保持组内上下文一致。

## 行为

### 文本泛化调度

普通模式前后端统一每批 16 个单元，最多同时处理两批（共 32 个单元）；整组模式最多同时处理两个完整组，保留原有组边界。共用 `web/text-studio-generation.js` 调度，每批返回后按原位置应用并串行保存。模型、推理强度、提示词和候选数量不变，当前一轮固定使用启动时的页面生成设置。后台音频准备仍只消费连续完成的前缀，因此后批先返回不会改变播报顺序。扩大批量后的实际耗时与输出质量尚需对照评估。

一批失败后不再派发新批次，已发出的另一批继续接收、保存；等待两批均结束后才允许继续泛化。保存失败会保留页面中的结果并显示错误，不宣称已落盘。切换项目或修改本批内容后，过期结果不会覆盖当前内容。

默认 Codex 命令增加 `--ephemeral --disable hooks`，减少会话文件写入和 hooks 开销（本机用户 hooks 为 Otty 状态通知）；仅作用于 Text Studio 的默认调用，不更改全局 Codex 配置、模型、推理强度或权限设置。项目文件与 Text Studio 请求/响应诊断日志继续保留。自定义 `TTS_TEXT_STUDIO_CODEX_CMD` 原样使用，不强行追加选项。需使用支持这些选项的 Codex CLI。

后端命令变更需重启 Text Studio；两批并行需刷新页面后开始下一轮泛化。不自动重启正在运行的服务。并行不能解决模型额度耗尽，也不保证耗时减半。

### 音频生成与播放

- 只预生成首轮作为启动库存；后续持续使用新随机组合，不自动重播首轮，不插入兜底音频。
- 保留现有合块边界规则和顺序。各单元的候选编号独立抽取，不固定种子，也不全篇统一抽一个编号。有其他组合时避免相邻整轮完全相同，但不保证每一句每次都换版本。
- 没有未 ACK 数量上限，也不因 Windows 高水位、低水位、缺少状态或离线而停止合成/发送。旧 LIVE_BUFFER_HIGH_SECONDS/LOW_SECONDS 环境变量不再参与控制，backpressure_active 状态兼容保留为 false。
- 人工 Pause/Resume/Stop、TTS 错误和网络错误处理保留。同步合成/入队请求不能被立即取消；Windows 已下载的音频由客户端控制。
- Windows 首次 startup buffer 保留；已经开播的会话，缓存耗尽后有短音频就恢复，不再等它凑够 12 秒。历史 buffering 元数据也按这条规则恢复。
- ACK、claim lease、WAV 预处理和内容缓存协议保持原样。ACK 代表接收完成，不代表播放完成。

## 缓存和内容

首轮文件保存在 runtime/prepared-live/<session_id>/，用于发送该首轮；不会用它无限循环补缺。Gateway 对完全相同文本与声音继续命中 runtime/tts-cache/，这属于正常合成请求复用，不是兜底选旧话术。停止后文件保留，不自动清理。

普通候选过滤仍核对候选编号、文本、命中位置和人工确认；完全被屏蔽的候选不参与随机选择。提前传输在全文首轮结束时接入最新完整候选池，后续轮次固定使用该池；进入后续轮次后修改候选需新开会话。首轮如选到实时日期/时间占位符，沿用准备前报错，以免批量准备过期时间。

只要实际 TTS 产出长期低于消费速度，首轮库存最终仍可能耗尽；本方案消除人为停产和额外 rebuffer 等待，不承诺凭空补足音频。

## 状态与生效

phase=streaming 表示首轮边准备边发送（总块数随泛化推进增长）；phase=preparing 表示旧完整稿路径的首轮准备；phase=playing 表示发送完整首轮或持续生成发送后续轮次，不代表 Windows 此刻一定在播放。prepared_segments/preparation_total_segments 显示首轮准备进度，preparation_total_rounds 固定为 1。round_number、generated_segments、total_segments 跟随当前发送轮次。

更新代码后需重启 Text Studio、刷新页面并新开会话。本次提前传输不修改 Windows 协议，无需重装客户端。不会创建新 Git 分支或 worktree。

## 提前传输验收场景

检查未完成稿首块 ready 后可启动、既有块立即发送、乱序返回的泛化批次不越过未完成前缀、追加块 sequence 连续、等待新文案不提前循环、全文结束进入第二轮；覆盖普通与整组模式。检查未发送编辑重新准备、已发送单元编辑仅作用于后续轮次、禁止播报不产生 sequence 缺号，以及暂停/继续/停止、TTS 永久错误、可重试错误、发送失败、音色变化和服务重启后的手动恢复。真实链路验收需核对 Mac 入队日志与 Windows 接收/播放日志。本次未执行自动化或 Windows 实机测试。
