## 1. 目标与顺序

先分清三个远端分支、额外的本地旧分支和两个工作目录，保护现有未提交成果，再决定分支整合及 Windows 优化范围。

执行顺序：重新盘点 → 纠正工作目录与分支对应关系 → 整理 main 未提交成果 → 处理播放优化补丁 → 决定 Windows 功能迁移。

继续使用同一个仓库。共用话术、审核、候选选择、分块和音频协议；按平台保留引擎启动、GPU 调度、凭证、数据目录、播放和打包差异。这里是组织方向，不要求先做大规模架构重构。

## 5. 分阶段任务

### A. 刷新盘点并确认没有并行写入

1. 重新读取 `git status --short --branch`、`git branch -avv`、`git worktree list --porcelain`。
2. 用 `git ls-remote --heads origin` 核对远端。若与本文不同，先更新差异表；不要直接覆盖或重置本地引用。
3. 对两处 worktree 分别核对工作区、未跟踪及 ignored 状态；不要输出凭证或运行数据内容。
4. 复查旧 Mac 分支仍是保留分支的祖先、没有新增独有提交。
5. 检查是否存在其他任务正在使用第二个目录。若有，先协调使用范围，不擅自切换。

验收：输出最新分支／目录矩阵、提交关系和未提交文件基线。将“代码已提交”“磁盘未提交”“已部署运行”分开表述。

### B. 纠正目录归属，处理旧分支

本阶段需在用户决定执行整理后进行。

1. 第二个目录保持干净且无其他任务使用时，将其切换到 `codex/windows-offline-runtime-v1`，不移动或删除目录。
2. 确认其 HEAD 与预期 Windows 分支一致，主工作区仍在 main，原有未提交成果完整。
3. 删除候选仅为本地 `refs/heads/codex/mac-runtime-reliability-v1`。记录旧 HEAD；取得该对象的明确删除授权后，使用正常安全分支删除流程，不强制删除。
4. 若安全删除失败，重新检查祖先关系和 worktree 占用，不升级为强制删除。
5. 本阶段不删除三个远端分支，不处理两个历史 stash。

验收：目录名与用途一致；旧分支删除与否如实记录；没有文件或运行数据丢失。

### C. 整理 main 的未提交成果

本阶段是提交准备与验证计划，不由本次“编写文档”请求自动触发。

1. 基于第 3 节六组内容建立文件／代码块归属，识别依赖再决定提交顺序。
2. 单独审查“取消背压”这一行为选择，不把它当作首轮准备不可分割的技术前提。
3. Windows 播放优化文档和探针需与 `5396416` 对照。main 尚未包含该提交时，说明文档不能被当作当前 main 已具备该实现的证据。
4. 修正文档中与最终配置冲突的描述，例如 CPU 默认值与新的 auto 配置。历史测试数字保留来源和日期，不宣称是本轮验证。
5. 完成相应验证后，按依赖形成可解释的提交；精确暂存，不使用一次性全量暂存把无关改动混入。
6. 音色注册需区分配置和实际模型资产；资产不存在的环境不能宣称音色可用。

验收：每份改动归属明确；提交边界合理；测试证据对应确切版本；未验证项、保留文件和剩余工作明确。

### D. 整合播放优化补丁

1. 在 main 未提交成果得到妥善处理后，确认 `5396416` 仍为未整合补丁，检查新增变化及冲突。
2. 按已授权的目标整合到 main，并验证播放顺序、会话切换、缓存变化、失败处理和 PCM16／Float32 路径。
3. Windows 单机版另有严格会话绑定及 `windows_playback_service.py` 入口。向该分支迁移时保留这些差异，不能用 main 播放器整文件替换。
4. 用隔离缓存运行诊断；真实 WinMM 测量必须在 Windows 上执行。模拟结果不等于设备播放验收。
5. 文档中的约 1557 ms → 69 ms 是历史同机对照，不作为新整合版本的自动验收结果。
6. 只有补丁在需要的目标中已被保留、验证完成且无需继续依赖此分支后，才提出本地／远端 `codex/windows-playback-gap` 的具体删除建议。删除另行授权。

验收：目标版本能追溯补丁，兼容两种部署入口，有明确测试证据和剩余限制。

### E. 由盘点结果决定 Windows 下一轮范围

本阶段先形成范围清单，再按用户后续指示实施，不因分支整理自动扩展为全功能迁移。

| 优先级 | 候选工作 | 已有代码证据或适配要求 |
| --- | --- | --- |
| P0 | 单机播放控制及重新开播 | 无界面服务只在首次绑定 Session，后续无重新绑定路径；页面暂停／停止主要控制生成。需隔离复现并定义生成与播放的联动 |
| P1 | 连续播放、合成失败恢复 | 评估播放切换补丁和 Live 层可控重试；保留严格顺序，不能自动跳过失败段 |
| P1 | 完整候选池参与随机播报 | 页面当前每段仅提交 `[selectedText(p)]`，需贯通全部候选及最终编辑内容 |
| P2 | 首轮准备与复用 | 接入 Windows GPU owner、音色配置和 `AI_LIVE_STUDIO_DATA`；不要写入 Program Files 内源码目录 |
| P2 | 清晰的运行状态 | 分开显示合成状态、播放状态、库存、等待原因与错误；确认 RTF 统计对实际 WAV 格式有效 |
| 后续 | 人工确认、整组泛化、全候选替换 | 按依赖迁移共用业务功能；不覆盖 Windows provider、DPAPI、运行时管理等代码 |

特别约束：

- Windows 分支已有 Vulkan、f16 KV cache、关闭两类 Flash Attention 的配置。Mac `start.sh` 的变化不是 Windows 提速方案。
- 本地 Ollama 与 CosyVoice 共享 GPU，不能直接启用当前 Mac 侧的泛化／TTS 后台并行；使用远程文字模型时另行判断。
- 不默认迁移“取消全部背压”。依据无缓存合成吞吐、播放消费速度和磁盘库存决定策略。
- 首轮库存不能解决长期产出低于消费；用 Windows 分支已有 `scripts/cosyvoice3-benchmark.py` 区分真实推理速度与缓存命中。
- 主线的新再缓冲行为与 Windows 原有严格模式并不完全相同，先比较机制，再决定迁移，避免机械叠加门槛。

建议第一轮功能验收：启动 → 开播 → 暂停 → 继续 → 停止 → 换稿／音色 → 再次开播；不重启软件、不播放旧会话、无无提示卡住。该验收目前未执行。
