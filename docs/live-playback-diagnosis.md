# 智播连续播放问题现状

更新时间：2026-09-14

> 当前 main 的复诊、现场数据和新增缺陷见 [2026-09-17 完整诊断](live-playback-diagnosis-2026-09-17.md)。本文保留历史背景，水位参数与建议不再代表当前实现。

## 一、当前现象

Text Studio 点击“开始智播”后，曾出现两类问题：

1. 首次启动或重新启动时提示 `HTTP Error 502: Bad Gateway`。
2. 502 修复后可以开始生成，但播放一段时间后，Mac 端不再及时生成，Windows 端缓存播放完后出现声音中断。

当前观察到的会话仍处于 `running`，但连续播放能力不稳定。

## 二、当前链路

```text
Text Studio
  → Live Session 选择当前话术
  → CosyVoice TTS 合成
  → Audio Cache 写入 WAV
  → Windows 客户端下载并播放
```

直播使用合成块。相邻短话术会合并成不超过 180 字的一个 TTS 请求，以减少频繁起音。

## 三、已经确认的证据

### 1. 502 的直接原因

Audio Cache 原来给 `/audio/enqueue` 使用 3 秒客户端超时。较大的 WAV 在服务端已经完成写入，但客户端先超时断开；服务端随后写响应时遇到断管，日志表现为一次 201 后跟一次 502。

因此当时的 502 不代表音频一定没有写入，部分失败块实际已经落盘。

这部分已经处理：音频入队单独使用 30 秒超时；缓存状态查询仍使用较短超时。

### 2. Metal 运行时不稳定

CosyVoice v0.1.1 和升级后的 v0.1.3 在 `auto/Metal` 冷启动时都出现过：

```text
GGML_ASSERT(ggml_are_same_layout(src, dst)
  && "cannot copy tensors with different layouts") failed
```

原生引擎进程因此退出，Gateway 返回 502。当前默认后端已切换为 CPU，Metal 仍可通过环境变量手动实验，但不适合作为当前默认路径。

### 3. CPU 生成速度低于播放速度

当前 CPU 日志中的典型数据：

| 项目 | 实测范围 |
| --- | ---: |
| 一个合成块的音频时长 | 约 24–36 秒 |
| CPU 生成一个合成块耗时 | 约 47–67 秒 |
| 合成速度相对播放速度 | 小于 1 倍实时 |

这意味着只要持续直播，缓存最终都会被播放端消耗完。缓存数量只能延后中断，不能从根本上消除中断。

### 4. 背压逻辑正在按设计工作

当前直播背压参数是：

```text
高水位：30 秒
低水位：12 秒
```

当 Windows 本地缓存达到高水位，Mac 会暂停新的 TTS 生成；缓存降到低水位后才继续生成。

这能防止 Mac 无限堆积 WAV，但在 CPU 生成速度不足时会形成如下循环：

```text
缓存达到高水位
  → 暂停生成
  → Windows 持续播放
  → 缓存降到低水位
  → 开始生成下一块
  → 下一块生成期间缓存继续下降甚至耗尽
  → 声音中断
```

## 四、当前状态快照

2026-09-14 15:39 左右观察到：

```text
Live Session: running
本轮合成块: 11 / 416
失败块: 0
Windows 本地缓存: 3 段 / 约 79 秒
背压: active
Audio Cache failed: 0
CosyVoice: CPU backend
```

所以当前的主要问题是“吞吐不足”，不是当前缓存文件大量失败。

## 五、增大缓存能解决什么

可以把高低水位从 `30 / 12 秒`提高到例如 `180 / 60 秒`或 `300 / 120 秒`。

这样可以：

- 让 Mac 多生成一些内容后再暂停；
- 增加短时间内的抗抖动能力；
- 降低偶发网络或落盘延迟造成的中断概率。

但它不能解决 CPU 长期小于 1 倍实时的问题。对于当前速度，缓存最终仍会下降到低水位并耗尽。

另外，`config/audio-cache.example.json` 中的 `preload_segments: 5` 只用于 `/audio/preload`，不会直接增加循环智播的生成缓存。

## 六、可选处理路线

### 方案 A：只增大缓存水位

建议值：`180 / 60 秒`。

优点：改动小、启动后立即生效。

缺点：只能延后中断；如果不增加“开始播放前预缓存”，冷启动时仍可能很快出现空档。

### 方案 B：增加启动预缓存

在 Windows 开始播放前，要求本地缓存达到指定时长，例如 60–120 秒。

优点：可以明显减少刚开始播放时的断音。

缺点：开始直播前需要等待；CPU 速度不足时，长时间直播仍然会逐渐追不上播放。

### 方案 C：普通话术整轮预生成

对于不含动态时间的普通话术，先生成一整轮并写入缓存，完成后再开始播放。

优点：一整轮生成完成后播放可以连续，最可靠。

缺点：启动等待时间长、占用磁盘；包含 `{{current_time}}` 等动态时间的段落不能过早生成。

### 方案 D：恢复稳定的高速 Metal 后端

修复或更换触发 `ggml_are_same_layout` 的 Metal runtime/build，使 TTS 速度恢复到至少 1 倍实时。

优点：最符合实时智播目标，也不需要无限增大缓存。

缺点：需要继续定位 native runtime 的 Metal 调度问题；仅升级到 v0.1.3 已经证明不够。

### 方案 E：多引擎并行生成

同时运行多个 CosyVoice 进程分担生成。

优点：理论上可以提高总吞吐。

缺点：模型内存占用显著增加，调度、顺序和动态时间一致性更复杂；当前不建议作为第一选择。

## 七、建议决策顺序

如果目标是“长时间连续直播”，建议顺序是：

1. 保留 CPU 作为稳定兜底，避免再次出现 Metal 原生崩溃。
2. 短期把缓存水位提高到 `180 / 60 秒`，并增加启动预缓存。
3. 长期修复稳定的高速 Metal runtime；否则整轮预生成是唯一能保证 CPU 播放连续的方式。
4. 动态时间段继续保持即将生成时替换，不能为了预缓存而在直播开始时提前固定时间。

## 八、验收标准

后续无论选择哪条路线，建议至少满足：

- 连续生成 10 个以上合成块无 502、timeout 或失败块；
- Windows 本地缓存不降到 0；
- 合成速度长期达到播放速度的 1 倍以上，最好保留 20% 以上余量；
- TTS 失败时能显示真实失败原因，不把缓存已落盘误报成 502；
- 动态时间在实际发起 TTS 时读取当前电脑时间。
