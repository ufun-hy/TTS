> 编写日期：2026-09-27，Asia/Shanghai。

## 1. 目标

完成 Windows 单机播放生命周期的剩余修复，确保调试源码、补丁包和完整安装包包含同一套实现，并在目标 Windows 上验证真实 TTS 与播放。

本阶段不迁移首轮准备、完整候选随机播报或更大范围的 main 功能。不以清理分支为前置条件，不重构整套运行时。

完整链路全部运行于同一台 Windows：

```text
Text Studio / Live Session
  → 本机 TTS Gateway / CosyVoice 生成 WAV
  → 本机 Audio Cache 队列（127.0.0.1:8000）
  → 本机 windows_playback_service.py 领取片段
  → WinMM 播放
```

“停止领取”指停止从本机缓存队列领取下一片段，不是停止从 Mac 下载。暂停生成、暂停领取和暂停播放是三个独立环节，需要联动。

## 3. 已发现的缺口

### W-01：暂停状态尚未阻止无界面入口领取

在固定起点中：

- `windows_playback_service.py` 的 `before_fetch()` 看到 `paused` 后调用 `playback.pause()`。
- `audio_client/client.py` 的 `run()` 随后仍执行 `fetch_next()`。
- `audio_cache/server.py` 的 `/audio/next` 直接调用 `manager.claim_next()`。
- `audio_cache/manager.py` 领取 ready 项时没有按会话控制状态筛选。

所以“暂停时已停止领取下一项”的历史验收描述超出了实际实现。现有测试通过也不能证明完整链路满足这一要求。

同时核查停止后积压的旧会话：清空动态绑定不代表旧 ready 项已经失去领取资格，必须防止下一次轮询重新绑定旧会话。该问题需通过隔离回归确认，不把尚未运行的复现写成测试结论。

### W-02：轻量补丁包缺少 Audio Cache 代码

`.github/workflows/windows-patch-build.yml` 当前仅复制 `server/`、`audio_client/`、`scripts/`、`web/` 和几个入口文件，没有复制本阶段需要的 `audio_cache/`；push 路径过滤也没有覆盖 `audio_cache/**`。

原样生成 ZIP 可能部署新客户端与旧缓存服务。现有“旧接口返回 404 时继续运行”的兼容路径还可能掩盖缺包，不能据此声明单机联动完整可用。

### W-03：构建通过与真机通过需分开

- 完整安装包工作流 `.github/workflows/windows-client-build.yml` 只自动监听 main 的 push，Windows 分支需显式选择对应 ref 触发，或调整为明确的构建规则。
- 固定起点的 Windows CI 测试列表未包含新增的 `tests.test_windows_playback_lifecycle`，需补入相关回归。
- WinMM 步骤使用 `continue-on-error: true`，CI 绿色不等于真实声音或生命周期通过。
- Windows 验收记录中写的“当前 HEAD”落后于实际分支；后续报告应记录“实际测试提交”，避免文档自身提交导致反复改写 HEAD。

## 4. 修复与验证任务

### A. 补齐暂停、继续、停止和新会话的控制链

1. 先追踪 GUI、无界面服务、客户端缓存恢复、服务端领取以及 Live 生成全部入口，找出共享控制点。
2. 单机模式暂停后，不再为该会话发起下一次合成，不再领取新的缓存项，并暂停本机播放器。
3. 同步合成或传输已经开始时，明确在途边界：不能假称立即取消；返回的旧结果不得绕过暂停／停止状态自动开始播放。
4. 暂停期间继续轮询控制状态，确保能够恢复；不能因停止取音频而停止接收继续指令。
5. 继续后恢复同一 Session 和正确 sequence，避免重复 ACK、重复播放或越过失败／缺失段。
6. 停止后禁止旧会话再次被领取或重绑，结束当前播放；新会话从 sequence 1 绑定。保留已有数据，不通过删除旧音频解决路由问题。
7. 不让暂停会话占住全局队首而阻塞其他合法会话；不通过“按最新下载时间”取代严格会话绑定。
8. 检查缓存服务不可用、控制接口缺失及进程重启时的行为。旧版远端客户端兼容与单机完整联动应明确区分；单机无法确认控制时要显示真实状态，不静默宣称暂停／停止已完成。
9. 保持现有 GPU owner、进程退出确认、Vulkan 配置和数据目录约定。

最低回归场景：

| 场景 | 验证结果 |
| --- | --- |
| 队列已有多段 ready 音频后暂停 | 播放暂停；没有新的该会话领取，未领项保持可继续处理 |
| 无界面入口暂停后继续 | 控制轮询未中断，正确恢复，不重复播放 |
| 下载中或合成中收到暂停／停止 | 在途结果不会直接播放；状态与实际行为一致 |
| 停止时仍有旧会话积压，再启动新会话 | 旧会话不能重新绑定，新会话从 sequence 1 播放 |
| sequence 缺失或某段失败 | 后续段不越过屏障，错误可见 |
| 存在未 ACK 的本地恢复项 | 恢复路径也遵守控制状态，不绕过暂停／停止 |
| 控制服务故障或旧接口返回 404 | 单机模式不误报联动成功；兼容范围明确 |

至少一项测试通过真实的隔离 HTTP Audio Cache 与无界面入口控制流程运行；TTS 和播放器可以用受控替身。不只测 GUI 标志位或直接调用 `PlaybackController`。

### C. Windows 源码调试

先准备目标 Windows、有效音频输出设备、外部模型和完整运行时。使用隔离测试数据目录；运行时端口固定，不能同时启动生产和测试两套服务。

以下命令在包含完整运行时的 Windows 项目根目录执行，路径按现场调整。只有源码 checkout 而无运行时的环境，先按构建说明准备依赖；不要把缺失运行时视为业务缺陷。

```powershell
.\scripts\windows-runtime.ps1 check -Models D:\AI-Live-Studio-Models -Data D:\AI-Live-Studio-TestData
.\scripts\windows-runtime.ps1 start -Models D:\AI-Live-Studio-Models -Data D:\AI-Live-Studio-TestData
.\scripts\windows-runtime.ps1 status -Data D:\AI-Live-Studio-TestData
```

如果源码与运行时分开存放，使用脚本已有的 `-Python`、`-BinDir` 指定子进程运行时，并确认脚本本身使用的 Python 可用。不将旧安装入口误当成新源码运行结果。

打开 `http://127.0.0.1:8770/`，执行“开播 → 暂停 → 继续 → 停止 → 换稿／音色再开播”。至少覆盖有积压库存、下载中、合成中、断粮恢复和缺段／失败段情形。

记录数据目录 `logs/` 下的 `text-studio.log`、`audio-cache.log`、`audio-client.log`、`tts-gateway.log` 和 `cosyvoice-server.log`。关联 Session、sequence、控制状态和时间，不输出 API Key 或大量完整话术。

测试后只停止本测试实例的已确认所属进程。生产实例的停止、替换与重启按用户已有授权执行，不按端口批量终止陌生进程。

3. 构建可能下载运行时依赖，模型仍外置。当前未推送的本地提交无法直接被远端 Actions 构建。
4. 完整产物位于 `build/windows/output/`，分发 Setup.exe 时同时包含全部 Inno 数据分片和校验文件。记录源码 SHA、构建记录与产物 SHA256。
