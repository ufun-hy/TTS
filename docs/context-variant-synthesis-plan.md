## 1. Current Flow

实际启动链路：`scripts/text-studio-start.sh` → `server/text_studio_entry.py` → Text Studio。入口把默认 Live manager 替换为 `SynthesisBlockLiveSessionManager`。

| 环节 | 当前实现与含义 |
| --- | --- |
| 编辑拆分 | `server/speech_units.py:speech_units`；完整句独立，超过 40 字的长句尝试按逗号及事实关联拆分。`split_paragraphs` 保留原段编号及来源偏移。 |
| 泛化请求 | `web/text-studio.html:generalizeAll` 从未完成单元中每次取 8 个；断点续作时这些单元不一定连续。单段重生成只提交一个单元。 |
| 模型上下文 | `server/text_studio.py:generalize_paragraphs` 最多每批 8 个单元；模型能看到整批，但提示词要求每段独立生成候选，没有组级 Variant 契约。不能说模型每次只看到一句。 |
| 结果校验 | `_validate_model_result` 校验段落存在和非空候选，未严格拒绝重复 ID、额外 ID、候选数量不足；随后截取至候选数。没有版本对应关系。 |
| 页面启动 Live | `liveCandidatePools` 实际传入 `candidates: [broadcastText(p)]`，只包含每段当前选中或人工编辑后的文本。普通页面入口目前并未传入所有候选，每轮通常重复同一稿。 |
| 后端随机 | `choose_candidate_round` 对传入的每段候选池独立随机；只有 API 收到多候选时，才会出现跨候选组合。避免重复整轮时还会单独更换一段。 |
| 合成分块 | `_round_segments` → `prepare_live_segments` → `_technical_chunks`，先固定 200 字硬切；随后 `prepare_synthesis_blocks` 按编辑段边界贪心装入 180 字目标块，并插入 `\n`。 |
| 输出 | 块级动态时间替换 → 现有重试合成 → Audio Cache → Windows。Gateway 默认每请求最多 200 字。 |

Text Studio 的直接泛化不经过 README 提及的 Timeline Semantic Coverage 流程。本任务应修改 Text Studio/Live 路径，不能只修改 `timeline/engine.py` 或时间轴 CLI。

## 2. Root Cause

代码可以证明的问题：

1. 批量请求只提供上下文可见性，不保证同一编号候选协同生成；独立重生成和人工逐句选择还会进一步改变句间关系。旧候选即使都选第 1 个，也不能视为完整 Variant。
2. 后端多候选随机以单元为单位，而页面目前只提交单一最终稿。新方案需要同时处理生成、保存、前端提交、整组选择；仅改随机函数无法完成目标。
3. TTS 分块发生在技术硬切之后，按段落装块没有自然句界搜索；重新拼接无法修复文本衔接，插入的换行是否增加韵律停顿仍需实测。
4. `server/prohibited_speech.py:filter_segments` 会过滤候选并压缩列表，`prepare_candidate_pools` 也会压缩空值。直接把候选下标视为跨段版本号会在这里失配。
5. `projectPayload` 及 `save_project` 明确构造保存字段；新增组数据若不贯穿保存、恢复、导出和 Live 提交，会静默丢失。现有事实修正还会调用独立泛化进行润色，需要保留组内上下文。

复现证据：

- 真实项目“女装风衣9.23”：886 个编辑单元，中位 23 字，最长 68 字，86 个来源段；64 个单元已有候选。只读检查，未修改项目。
- 将其前 16 个单元的全部候选交给后端，固定随机种子 42，选择编号为 `1,1,3,2,2,2,1,5,1,5,4,1,1,1,2,2`，生成 163/158/49 字三块，共插入 13 个换行。此为后端多候选路径复现，不代表当前页面实际提交。
- 按页面规则为 `p0003–p0009` 构建单候选池，两轮结果完全相同，当前合成块长度 153 字。
- 构造 `194 个“甲” + 可以自己自由调节的系带设计。`，当前硬切得到 `…可以自己自由` / `调节的系带设计。`。

以上能确认结构缺陷，不能代替真实 CosyVoice 听感验证，也不能据此把所有听感问题归因于换行。

## 3. New Generalization Structure

目标链路：编辑单元 → 连续上下文组 → 一次生成多套整组 Variant → 每轮每组选定一个 Variant → 连续文本及来源映射 → 自然标点合成块 → 现有 TTS/缓存/播放链路。

三个职责保持独立：

- 编辑单元：保留 `p0001` 等 ID、原文与定位，服务搜索、风险检查、人工编辑。
- 上下文组：相邻单元共同生成完整版本；负责事实和跨句衔接，不受 200 字 TTS 上限限制。
- 合成块：根据实际选定、过滤并展开动态内容后的文本重新切分；不把编辑单元或组边界强制转换为换行/音频边界。

分两步实施：先做小范围实验模块和独立 A/B/C 脚本，调用现有 Provider 与 TTSClient；听感达到目标后，再接入页面、项目持久化和 Live。实验阶段不改生产默认行为、不将测试音频投入 Windows 队列。

## 4. Variant Data Structure

建议保存为 schema v2。保留 `paragraphs[].candidates` 字符串数组作为编辑文本的唯一持久化来源；组记录原始单元有序列表和显式 Variant ID 到共同候选槽位的映射。不要再存一份独立的整组全文，避免编辑不同步。

```json
{
  "schema_version": 2,
  "paragraphs": [
    {"id": "p0001", "original_text": "原句一。", "candidates": ["版本一的首句。", "版本二的首句。"]},
    {"id": "p0002", "original_text": "原句二。", "candidates": ["版本一的承接句。", "版本二的承接句。"]}
  ],
  "context_groups": [{
    "id": "g0001",
    "revision": 1,
    "paragraph_ids": ["p0001", "p0002"],
    "source_fingerprint": "sha256-of-ordered-ids-and-generation-inputs",
    "selected_variant_id": "g0001-r1-v1",
    "variants": [
      {"id": "g0001-r1-v1", "candidate_index": 0},
      {"id": "g0001-r1-v2", "candidate_index": 1}
    ]
  }]
}
```

模型输出以 Variant 为外层：`variants[{id, segments:[{id:"p0001",text:…},{id:"p0002",text:…}]}]`。要求每套版本按完整表达生成，再映射回原单元；不允许通过重新分句猜测映射。程序严格验证后转置成上述候选数组。

必要不变量：

- 每组成员连续、有序、无重复；所有单元被恰好一个组覆盖，组与项目 ID 一致。单元数、全文与候选字符数均有有限上限。
- 每套 Variant 恰好覆盖预期成员一次；缺失、重复、额外 ID、空值、非字符串、候选数量不一致均拒绝整组结果，不截断、不复制补齐、不拼接新旧结果。
- 候选槽位在该组 revision 内固定，不对任意一个成员单独删除、去重或压缩数组。整个 Variant 淘汰时按 ID 禁用；整组再生成时原子替换并增加 revision。
- 每轮按组保存选择结果 `{group_id, revision, variant_id}`，组内所有成员使用同一候选槽位。避免重复时更换一个完整组的 Variant，不更换单独一句。
- 多组之间的 `v1` 没有天然共同生成关系。每组分别选择；边界衔接通过分组策略与只读邻接上下文改善，不能声称这等于全文一次共同生成。

编辑与兼容：

- 切换候选时切换该组预览版本；单句编辑仍只修改该 Variant 的对应单元，标记该组需重新检查，并让风险、搜索、试听读取同一份候选文本。
- 重生成入口明确为“重生成所在上下文组”。先保留当前版本，完整生成并校验成功才应用；失败保留全部旧候选。已有人工编辑不由单句按钮隐式覆盖，应提供新版本预览后应用。
- 批量事实修正保留候选槽位；如需模型润色，对受影响的整套 Variant 提供完整上下文，限制修改目标单元，其他成员保持不变。
- 原文、事实配置、成员顺序变化使对应组 fingerprint 失效，需要重新生成/审核。候选人工编辑使风险结果失效；输入 fingerprint 不使用候选全文。
- 新组模式在服务端校验后先完成整组选取，再执行句级禁止播报过滤；过滤仅影响本轮发音文本和来源映射，不修改候选池。不可绕过现有禁止播报规则。
- 若过滤造成整套版本部分成员完全消失，保留原候选及定位并标记需复核；组模式启动前排除这种未确认的版本。没有可用版本则报告具体组，禁止静默换用其他段的候选。部分句子删减也应在组预览中可见。
- schema v1 不自动迁移、不伪造版本对应关系。旧项目仍可按当前最终稿播放；升级通过复制/重新生成完整组进行。新组数据缺失、过期或半组完成时不能静默退回逐段随机。
- 新 Live 请求增加组模式的明确字段和 `context_groups`；旧 `segments` 请求继续兼容。项目保存、恢复和备份 JSON 携带完整组数据；最终稿 TXT 仍只是当前整组选择的派生输出。

## 5. Context Grouping Strategy

初始实验参数：通常 3–6 个相邻编辑单元、约 120–240 字；以自然结束位置为主，不硬凑数量。极短附和句和被逗号拆开的连续句可以使组超过 6 个单元。单组输入软上限约 360 字，单个超长编辑单元完整保留并由既有 4000 字限制约束；候选输出另设明确上限。

1. 优先利用 `source_paragraph_index`、句末强标点和来源偏移。普通段落边界是优先切点，不是绝对断点：真实风衣稿有上一原段结束于“是吧”，下一原段才报价格的连续表达。
2. 不在逗号结尾、未完条件或明显承接词前强制结束组；保守复用现有事实组合、引号/括号、数字保护规则。没有安全边界的长输入允许单独成组，不先按字数破坏原稿。
3. 向模型提供前后各一个邻接单元作为只读上下文，并注明不输出、不重复邻段信息。组内共同生成 N 套版本，保持事实、顺序、口吻；不能用额外上下文代替整组输出契约。
4. 组在完整项目顺序上先建立并持久化；续作只选择未完成/失效的组，不将稀疏的未完成单元打包成新组。批大小只是请求调度设置，不是组定义。
5. 首轮按一个组一个请求控制输出和失败范围，整组校验、保存和重试。不要先增加并行 Provider 调度。

这些是启发式参数，不是已验证的最佳值。旧项目缺少来源偏移时按现有顺序和标点退化处理，并在实验记录中标明。

## 6. Semantic TTS Block Strategy

在任何技术切片之前恢复已选 Variant 的连续文本，保留每个字符区间到 `{group_id, variant_id, paragraph_id}` 的映射。合成块可以包含多个组的末尾/开头；编辑单元、上下文组、音频块不要求一一对应。

- 相邻中文单元已有标点时直接拼接，不插入 `\n`。保留源文本明确的段落边界为边界元数据，不把所有排版换行都当作停顿。拉丁字母/数字词边界需要保留分隔空格，避免单词粘连；不机械补句号。
- 禁止播报过滤在自然合成分块之前执行，保留被删除部分的定位；避免将敏感句拆开后漏检。跨编辑单元的连续句应在恢复后检查，过滤结果需要映射回单元。
- 目标 160–180 字，120–180 字是偏好区间；200 字是当前 Gateway 默认硬上限。每次实际请求按最终文本再次检查长度。
- 优先选择目标附近、上限以内的句号、问号、感叹号、分号边界；其次逗号、顿号等弱边界。目标前没有合适边界时允许向后找到不超过 200 字的自然结束点，不为严格凑 180 字提前截断。
- 对引号/括号闭合、数字小数/千分位、连续标点和英文词做保护；句末引号跟随前句。很短尾块尝试在安全自然边界调整，不通过截词补长度。
- 无任何安全标点/空格且超长才硬切；记录 `hard_cut` 和来源位置，供人工检查。标点规则只能近似自然语义，不能保证无标点长文本的语言完整性。
- 动态时间仍在接近实际合成时展开，展开后再检查/必要时重新分块，且只在已知占位符完整边界操作。不要在整轮预生产前数分钟冻结全部动态时间。重试复用同一已解析的块，不改变文本或序号。
- 新组路径绕开“先 200 字硬切再合并”；普通 Live 与实际 SynthesisBlock 入口都要有明确策略，避免入口不同得到不同分块。受保护的重试、背压、缓存标识和序号逻辑保持原有职责。

块记录至少包括唯一块 ID、最终文本、来源成员/区间与切分原因；当前只保存首段 ID 不足以完成合成错误定位。序号仍由现有 Session 递增。

## 7. A/B Listening Result

**尚无真实 A/B/C 音频或主观评分，本阶段不能报告 C 已接近 A。**

已确定首轮素材：项目“女装风衣9.23”（`20260923-180442-1bba64df`）的 `p0003–p0009`，7 个相邻单元共 134 字，每个已有 5 个旧候选。它覆盖面料、季节、内搭和穿着效果，可在 200 字上限内做真正一次请求的 A 基线。实验使用只读快照，正式项目不变。

| 版本 | 文本与合成方式 | 用途 |
| --- | --- | --- |
| A | 该片段完整原稿，单次 `/synthesize` | 原稿连续表达参照；不提高 Gateway 限制，不换 backend。 |
| B | 该片段旧候选独立选取、固定随机种子，走当前硬切/换行 block | 用户任务定义的旧泛化与独立随机对照；明确其不同于当前页面单候选提交。 |
| C | 相同片段一次生成完整 Variant，整组选择、连续拼接、自然 block | 验证新链路。 |

补充对照 B-ui：按页面当前选中稿合成；当前只读模拟为一个 153 字块。A/B/C 三版都不足 200 字时，主要验证泛化衔接与换行；不能据此证明长文本分块改善。随后扩展同一项目到 600–1000 字、多个完整组，验证组间衔接、块边界及长句处理；长稿 A 按原稿自然段分块并明确标为“原稿自然块”，不可称为全文单次合成。

为区分变量，可用同一套 C Variant 分别合成 `\n` 拼接与连续标点拼接，或把相同 B 文本交给新旧 block builder。只在主要 A/B/C 差异不足以判断时扩大实验。

控制条件与记录：

- 固定同一音色（素材项目现用 `speaker_c`）、模型、backend、参考提示音、语速和音量；不调用现有会改变 reference/backend 的其他 A/B 脚本。
- 复用本项目 Provider 调用及 TTSClient，文本种子与 Variant ID 写入 manifest。B 优先使用现有候选；若比较生成方法本身，再用与 C 相同 Provider/Model 重生成 B，区分两个实验。
- TTS Result Cache 可能复用相同文本；记录命中/复用事实，不删除缓存、不把命中结果算作独立重复采样。模型随机参数若现有接口不可控，标为未固定。
- 实验音频直接保存到 `runtime/ab/context-variants/<run-id>/`，不入实际 Live/Windows 队列。保存 source 快照、Provider 输入输出、各轮选择、块文本/边界/字数、实际设置、耗时和音频。
- 连续试听文件用现有音频处理能力统一格式后按原样拼接，不额外加静音、交叉淡化或自动裁尾；保留单块 WAV 和边界时间，避免后期处理掩盖问题。
- 提供去除方案标签的 X/Y/Z 试听顺序及映射；评分包含承接、语气连续、重起调频度、停顿、重音、情绪和直播感，每项 1–5 分，保存具体问题时间点。
- 首轮至少比较 3 套完整 C Variant 对应的 B 组合；主观验收需实际试听者确认。代码测试、块数减少、RTF 改善均不能替代“C 听感明显接近 A”。

环境只读检查：Gateway `/health` 返回 200，队列 ready，引擎 sleeping，`active_requests=0`、`queue_depth=0`。休眠不是故障，但这不证明唤醒与真实合成成功。本阶段未读取 Keychain、未调用 Provider/TTS、未启动播放。

## 10. Remaining Risks

- 一次生成一组只保证模型共同看见上下文，不能机械证明语义、事实和听感正确。结构校验之外仍需现有事实/风险检查和真实试听。
- 多组分别生成的接缝仍可能不自然。只读邻接上下文和边界策略能降低风险，无法等同全文联合生成。
- 人工单句修改、事实修正和禁止播报删句会改变衔接，需要组级预览和审核失效机制；不能把“保留 ID”误当作“保持连贯”。
- 更大的输出增加 Provider 超时/JSON 错误概率；先一个组一个请求，按组恢复，不扩展无关并发调度。
- 200 字上限仍然使长稿必须多次 utterance，不能承诺与完整长文一次合成完全相同。
- 单位/字数规则不能识别所有真正语义边界；硬切应可追踪，实验结果决定是否需要更复杂边界策略。
- 当前历史项目没有整组共同生成证据，重新泛化需要时间，不能无损把旧候选“补标签”升级。
